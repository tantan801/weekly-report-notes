### 2）iMX 项目 Linux 系统启动流程（U‑Boot → Kernel → Rootfs），含源码调用流程

整体三段式：**Bootloader（U‑Boot）→ Linux 内核（Kernel）→ 根文件系统（Rootfs）**。

#### 2.1 U‑Boot 阶段（源码调用链）

```text
arch/arm/lib/vectors.S  _start
   └─ b reset
        └─ save_boot_params → save_boot_params_ret
             └─ cpu_init_cp15 / cpu_init_crit
                  └─ _main  (arch/arm/lib/crt0.S)
                       ├─ board_init_f()        /* 第一阶段：在 OCRAM 中初始化 DRAM 等 */
                       └─ board_init_r()        /* 第二阶段：在 DDR 中跑完板级初始化 */
                            └─ main_loop()       (common/main.c)
                                 └─ 倒计时未打断 → cli_loop() (common/cli.c)
                                       ↓ 用户敲 bootz / 执行 bootcmd
                                 do_bootz() → do_bootm_states()
                                       └─ boot_fn = do_bootm_linux()   (boot_prep_linux)
                                             └─ image_setup_linux()
                                                  └─ image_setup_libfdt()
                                                       └─ fdt_chosen()   (common/fdt_support.c)
                                                            /* 把 U‑Boot 的 bootargs 写入内存中 dtb 的 chosen 节点 */
                                             └─ boot_jump_linux()
                                                  /* 设置 r0=0, r1=machine, r2=dtb 物理地址，跳到内核 stext */
```

关键结论：**bootargs 不是写在内核里的，是 U‑Boot 在启动前动态塞进 dtb 的 chosen 节点**（见《设备树实验》5.6 节）。

#### 2.2 Kernel 阶段（源码调用链）

```text
arch/arm/kernel/head.S  ENTRY(stext)
   ├─ __lookup_processor_type   /* 校验 CPU ID */
   ├─ __create_page_tables      /* 建页表 */
   ├─ __enable_mmu → __turn_mmu_on   /* 开 MMU，此后跑虚拟地址 */
   └─ start_kernel()            (init/main.c)
        ├─ setup_arch()         /* 架构初始化，解析设备树 */
        │     └─ setup_machine_fdt() → of_flat_dt_match_machine()
        │     └─ unflatten_device_tree()  /* dtb 展开成 device_node 树 */
        ├─ ...
        └─ rest_init()
             └─ kernel_thread(kernel_init, ...)
                  └─ kernel_init()   (PID=1)
                       ├─ kernel_init_freeable()
                       │     └─ 解析 U‑Boot 传来的 bootargs，拿到 root= 等参数
                       └─ 挂载真正的根文件系统（见 2.3）
                       └─ run_init_process("/sbin/init")  /* 切到用户态 */
```

#### 2.3 Rootfs 阶段

```text
内核挂载 root= 指定的真实根文件系统（如 /dev/mmcblk1p2，EXT4）
   └─ 执行根文件系统里的 /sbin/init（BusyBox init）
        └─ 解析 /etc/inittab → 执行 /etc/init.d/rcS
             ├─ mount -a        /* 读 /etc/fstab，挂 proc/sysfs/tmpfs 等虚拟文件系统 */
             ├─ echo /sbin/mdev > /proc/sys/kernel/hotplug   /* 开 mdev 自动建 /dev 节点 */
             └─ 启动 shell / 业务程序
```

> 一句话：**内核态挂载真实 rootfs，用户态脚本再挂载 proc/sysfs/tmpfs 等虚拟文件系统。**

### 3）怎么升级 U‑Boot / Kernel / FDT / Rootfs

两套方案（都来自《系统移植梳理》第 4 节）：

**方案一：MfgTool 整包烧写（适合量产/变砖救援）**
1. 准备 `u-boot.imx`、`zImage`、`imx6ull-alientek-emmc.dtb`，并把 rootfs 打成 `rootfs.tar.bz2`
2. 板子拨到 USB 下载模式，连 OTG，双击 `.vbs` 点 Start
3. MfgTool 内部：临时在 DDR 起一套 Linux → 给 eMMC 分区/格式化 → 写 u-boot 到裸扇区 → 写 zImage/dtb 到 FAT → 解压 rootfs 到 EXT4
4. 拨回 eMMC 启动，重启

**方案二：U‑Boot 命令行 + TFTP 单件升级（适合日常调试，注意 uboot 易变砖）**

```bash
# 进 U‑Boot 命令行，网口连通，Ubuntu 开了 TFTP
# —— 升级 u-boot.imx（裸扇区，无文件系统）——
tftp 80800000 u-boot.imx
mmc dev 1
mmc write 80800000 0x2 0x400        # 直接写物理扇区

# —— 升级 zImage（FAT 分区 mmc1:1）——
tftp 80800000 zImage
mmc dev 1
fatwrite mmc 1:1 80800000 zImage ${filesize}

# —— 升级 dtb（FAT 分区 mmc1:1）——
tftp 80800000 imx6ull-alientek-emmc.dtb
mmc dev 1
fatwrite mmc 1:1 80800000 imx6ull-alientek-emmc.dtb ${filesize}

# —— 升级 rootfs（EXT4 分区 mmc1:2）——
# 先 NFS 挂载启动，让 mmc1:2 空闲，再把新 rootfs 复制/解压进去
```

### 4）四大件在 eMMC/SD 卡的位置，是裸数据还是带文件系统

（来自《系统移植梳理》3.1/3.2）

| 资源 | 存放位置 | 分区类型 | 说明 |
|------|----------|----------|------|
| **u-boot.imx** | eMMC/SD 头部、分区表之前的原始扇区 | **裸数据 raw，无文件系统** | 直接写物理扇区；写错直接变砖 |
| **zImage（内核）** | mmc1:1 / mmc0:1 | **FAT 文件系统** | 可用 `fatload`/`fatwrite` |
| **dtb（fdt）** | mmc1:1 / mmc0:1 | **FAT 文件系统** | 和 zImage 同一 FAT 分区 |
| **rootfs** | mmc1:2 / mmc0:2 | **EXT4 文件系统** | Linux 根文件系统 |

> eMMC 版本设备号 `mmc dev 1`；SD 卡版本 `mmc dev 0`。

### 6）理解 MMU 吗，有什么作用

**MMU（Memory Management Unit，内存管理单元）**，作用两点（来自《LED 驱动开发实验》41.1.1）：

1. **地址映射**：把 CPU 看到的**虚拟地址（VA）** 翻译成硬件真实的**物理地址（PA）**
2. **内存保护**：设置每段内存的访问权限（读/写/执行）、cache 属性等

裸机（关 MMU）直接操作物理地址；Linux 内核开着 MMU，CPU 全程访问虚拟地址。

---

### 7）驱动里可以直接访问物理内存吗，为什么一定要 ioremap

**不能直接访问物理地址。** 因为 Linux 内核开启 MMU 后，CPU 发出的全是虚拟地址，MMU 会做地址翻译+权限检查。如果你在驱动里直接拿 `0x020E0068`（GPIO 复用寄存器物理地址）去读写：

- 该地址没有在内核页表里建立映射，访问会触发 **prefetch abort / 段错误**；
- 即使侥幸命中，也绕过了 cache/内存属性，行为不可预期。

所以必须用 **`ioremap(phys_addr, size)`** 把物理地址映射成内核虚拟地址（返回 `void __iomem *`），之后用 `readl/writel` 这类专用 IO 函数去操作。

> 《LED 驱动开发实验》里 GPIO1_IO03 复用寄存器物理地址是 `0x020E0068`，裸机直接写它，Linux 驱动必须先 `ioremap` 再 `writel`。

---

### 8）MMU 是硬件还是软件管理单元

**MMU 是硬件单元**（集成在 SoC/CPU 内部，Cortex‑A 系列必有）。但它需要**软件（操作系统）配合**：

- 硬件负责：根据页表把 VA 实时翻译成 PA，并做权限/cache 检查；
- 软件负责：建立、维护、切换页表（内核 `mm` 子系统），配置 TTBR 等寄存器。

所以它本质上是"**硬件做翻译，软件管页表**"的协同单元。

### 9）dts 和 dtsi 的区别

（来自《设备树实验》43.1 / 43.3）

- **`.dts`**：板级设备树，描述**某一块开发板独有**的硬件（如 `imx6ull-alientek-emmc.dts` 描述 ATK 板子上的外设）。
- **`.dtsi`**：设备树头文件，描述 **SOC 芯片公共**硬件资源（CPU、UART、I2C、SPI 等控制器），多个 dts 通过 `#include` 引用同一个 dtsi，类似 C 头文件。

```c
/* imx6ull-alientek-emmc.dts 里 */
#include "imx6ull.dtsi"     // 芯片公共外设（SOC 内部）
// 板级独有内容写在本文件
```

> 核心思想：把板级硬件信息从内核 C 代码剥离到独立的 dts/dtsi；换板子改 dts 重编 dtb 即可，不用重编 zImage。`imx6ull.dtsi` 严禁直接改，板级改动用 `&label` 在 dts 里追加。

### 10）启动的第一个分区在哪定义？SD 卡与 eMMC 的分配不同

**"第一个分区"≠启动起点。** 真正的启动起点是 **u-boot.imx 所在的裸扇区**（分区表之前），然后才是第一个文件系统分区。

**SD 卡（mmc0）分配：**

```text
sector 0        : MBR 主引导记录 + 分区表
sector 1 (1KB)  : u-boot.imx 裸写（IVT+DCD+u-boot），raw，无文件系统
分区 mmc0:1     : FAT32  → zImage + dtb
分区 mmc0:2     : EXT4   → rootfs
```

**eMMC（mmc1）分配：**

eMMC 除了"用户数据区 UDA"，还有**硬件物理分区** Boot1 / Boot2 / RPMB（见第 11 题）。两种常见做法：

- **做法 A（笔记里的做法）**：把 u-boot.imx 裸写到 UDA 最前面（raw，例如 `mmc write 80800000 0x2 0x400` 写到 UDA 扇区 2），然后 UDA 里建分区表：
  ```text
  UDA 头部 raw   : u-boot.imx（裸数据）
  UDA 分区 mmc1:1: FAT32 → zImage + dtb
  UDA 分区 mmc1:2: EXT4  → rootfs
  ```
- **做法 B（更标准）**：把 u-boot.imx 烧进 eMMC 的 **Boot 物理分区**（boot0/boot1），用 `mmc partconf` 配置 Boot ROM 从 Boot 分区启动，UDA 全部留给 FAT+EXT4。

> 分区表（mmc0:1/0:2、mmc1:1/1:2）是烧写工具（MfgTool/SD 卡制作脚本）写入的；u-boot.imx 的裸位置是 NXP 规定的固定偏移。两者"位置"的定义来源不同。

### 11）eMMC 是什么，有哪些分区，各分区干什么，iMX 的 uboot 在哪个物理分区

**eMMC = embedded Multi‑Media Controller**：把 NAND Flash 颗粒 + 闪存控制器 + 标准接口封装在一颗芯片里，对外的接口和协议类似于 SD 卡，但焊死在板子上、容量/可靠性更高。

**eMMC 的物理分区（硬件级，由 eMMC 控制器划分）：**

| 物理分区 | 作用 |
|----------|------|
| **Boot1 / Boot2** | 启动分区，专门放 bootloader（如 u-boot）。Boot ROM 可配置从某个 Boot 分区启动 |
| **RPMB** | Replay Protected Memory Block，安全区，存指纹/密钥等防回放数据，普通系统读写不了 |
| **UDA（User Data Area）** | 用户数据区，主力存储；FAT（zImage/dtb）、EXT4（rootfs）就建在这里 |

**iMX 的 uboot 在哪个物理分区？**
- 笔记里的烧法（`mmc write ... 0x2 ...`）是把 u-boot.imx 写到 **UDA 头部 raw 区**；
- 若用标准 Boot 分区方案，则放在 **Boot1 或 Boot2** 物理分区。
- 实际从哪个启动，由 eFUSE/引导配置 + Boot ROM 决定，不是"放哪都行"。

### 12）`$(MAKE) -C $(KERNELDIR) M=$(CURRENT_PATH) modules` 每个参数含义

（来自《字符设备驱动开发入门》1.4.3 Makefile）

```makefile
KERNELDIR := /home/.../linux-imx-...     # 内核源码绝对路径
CURRENT_PATH := $(shell pwd)             # 当前模块源码目录
obj-m := chrdevbase.o                    # 把 chrdevbase.c 编成外部可加载模块 .ko
$(MAKE) -C $(KERNELDIR) M=$(CURRENT_PATH) modules
```

| 片段 | 含义 |
|------|------|
| `$(MAKE)` | 递归调用 make（保留原 make 的 `-j` 等参数） |
| `-C $(KERNELDIR)` | 先切换到内核源码目录去执行 make（借用内核的 Kbuild 体系） |
| `M=$(CURRENT_PATH)` | 告诉内核：外部模块源码在 `M` 指定的目录，编译完把 `.ko` 放回这里 |
| `modules` | 内核 Makefile 的目标，含义是"编译外部模块" |

> 没有 `-C ... M=...`，单靠模块目录的 Makefile 是编不出正确 `.ko` 的——必须借用内核源码的编译规则、头文件和符号表。

### 14）编译 `j32` 什么意思？`make j32` / `make -j32` / `make -j 32` 哪种写法对

`-j N` 是 make 的**并行编译**参数，意思是"同时开 N 个 job"加速编译（N 一般取 CPU 核心数，32 就是 32 路并行）。

- ✅ **`make -j32`**（笔记里用的就是这个，如《LED 驱动开发实验》《pinctrl 实验》）：**正确，推荐写法**
- ✅ **`make -j 32`**：也正确，`-j` 和数字之间有空格 GNU make 同样接受
- ❌ **`make j32`**：**错误**，`j32` 会被当成"名为 j32 的 make 目标"去执行，而不是并行参数

> LED/pinctrl/gpioled 实验的 Makefile 里写的都是 `make -j32`，照这个用就行。

### 15）DTS 里声明的外设，内核就一定会加载吗

**不一定。** 两个条件都要满足：

1. **`status` 属性**：`status = "okay"` 才会被启用；`status = "disabled"`（或缺失）内核直接忽略该节点（见《设备树实验》43.3.3）。
2. **必须有匹配的驱动**：即使 `status = "okay"`，如果内核里没有 `compatible` 能匹配上的 platform/总线驱动，节点只是安静地出现在 `/proc/device-tree` 里，**不会 probe、不会真正加载**。

所以"声明≠加载"，驱动匹配 + 状态使能两者缺一不可。

### 16）BROM 的固件存在哪里，做了哪些工作，它加载的固件运行在什么上面

- **BROM 在哪**：BROM = **Boot ROM**，是芯片内部的**掩膜 ROM（mask ROM）**，出厂固化、不可改，CPU 上电第一条指令就在这里。
- **做了什么**：
  1. 读 **BOOT_MODE 引脚 / eFUSE**，决定从哪个设备启动（SD / eMMC / NAND / USB 等）；
  2. 初始化最基础的外设（一般是只读的、够用的小配置），从启动设备读取**第一个启动镜像**（iMX6ULL 上是 `u-boot.imx`，内含 IVT + DCD + u-boot）；
  3. 校验（若开启安全启动）/ 加载该镜像到**芯片内部 OCRAM**；
  4. 跳转到镜像入口，把后续启动交给它。
- **加载的固件运行在哪**：BROM 自己跑在 CPU + 内部 ROM/OCRAM 上；它加载的 u-boot 一开始也跑在**内部 OCRAM**（DDR 还没初始化），等 DCD 把 DDR 初始化好后，u-boot 才搬到 DDR 跑（见 17/18 题）。

---

### 17）SPL 运行在芯片内部 RAM 上吗，不是在 DDR 上吗

**SPL 运行在芯片内部 SRAM（OCRAM）上，不在 DDR。** 原因：SPL 是"二级程序加载器"，它出现得比 DDR 初始化还早——**DDR 还没起来，根本没法用**，所以 SPL 只能挤在芯片自带的那点 OCRAM 里跑，职责就是**初始化 DDR、时钟、电源**，然后把下一阶段（ATF / TEE / u-boot）从存储设备搬到 DDR 去执行。

> 特别注意 **iMX6ULL 的标准流程里没有 SPL**：它靠 `u-boot.imx` 头里的 **DCD（Device Configuration Data）** 由 Boot ROM 直接把 DDR 初始化好，然后 u-boot 直接在 DDR 里跑（见 18 题）。而 **RV1126 这类平台才用 SPL**（先 SPL 在 OCRAM 初始化 DDR，再加载后续）。所以"有没有 SPL"正是 iMX6ULL 和 RV1126 启动链的一个差别（见课后思考）。

---

### 18）DDR 的初始化是谁做的

分平台：

- **iMX6ULL（无 SPL 流程）**：DDR 初始化由 **u-boot.imx 里的 DCD 块**完成。**DCD 是镜像头里的一段配置数据，由 Boot ROM 在跳进 u-boot 之前就按表写寄存器把 DDR 控制器配好**。也就是说，u-boot 一开始就能在 DDR 上跑，是因为"DDR 早在 BROM 阶段就被 DCD 点亮了"。
- **RV1126（有 SPL 流程）**：DDR 初始化由 **SPL** 在 OCRAM 里完成，然后 SPL 把 ATF/TEE/u-boot 加载到 DDR。

> 结论：**DDR 初始化发生在 u-boot 之前**，由"更底层的家伙"（iMX6ULL 是 BROM 执行 DCD；RV1126 是 SPL）完成，而不是 u-boot proper 或内核。

### 19）ARMv7 和 ARMv8 的区别

| 维度 | ARMv7‑A（如 iMX6ULL 的 Cortex‑A7） | ARMv8‑A（如 iMX8 / RK3399 等） |
|------|-----------------------------------|--------------------------------|
| 位宽 | 仅 32 位（AArch32） | 引入 64 位（AArch64），同时兼容 32 位 |
| 地址空间 | 32 位，最大 4GB | 64 位虚拟地址，支持超大物理/虚拟空间 |
| 寄存器 | 16 个 32 位通用寄存器 | 31 个 64 位通用寄存器（X0‑X30） |
| 异常模型 | 老式异常向量 + 模式切换 | 全新异常等级 EL0/EL1/EL2/EL3（安全/虚拟化更清晰） |
| 安全扩展 | TrustZone 有，但 EL3 概念弱 | 标配 EL3 安全监视器，**ATF/TF‑A 原生基于 EL3** |
| 典型 SoC | iMX6ULL（Cortex‑A7） | iMX8M（Cortex‑A53）、RK3399 等 |

> 顺带澄清一个常见误会：**RV1126 的 CPU 本身是 Cortex‑A7，仍属 ARMv7‑A**；它和 iMX6ULL 在"启动多了 SPL/TEE/ATF/eFUSE"这件事上，更多是因为**芯片安全启动架构/方案不同**，而不是单纯因为 ARMv7 vs ARMv8。ARMv8 因为有了干净的 EL3，才让 ATF 成为标准件（见课后思考）。

### test1 —— 驱动 demo（ko + insmod/rmmod + printk 等级 + proc 子节点）

**需求**
1. 写一个 ko，可以 `insmod` / `rmmod`；
2. 内核打印有 8 个等级，控制台按等级过滤输出；
3. 在 `/proc` 下生成驱动子节点，读取时打印 ko 信息，写入时把数据传给驱动并用 printk 打印出来。

#### 2.1 内核打印等级（8 级，数字越小优先级越高）

来自《字符设备驱动开发入门》1.4.1，`include/linux/kern_levels.h`：

| 等级 | 宏 | 含义 |
|------|----|------|
| 0 | KERN_EMERG | 系统不可用（内核崩溃） |
| 1 | KERN_ALERT | 必须立即处理 |
| 2 | KERN_CRIT | 严重错误 |
| 3 | KERN_ERR | 错误（驱动常用） |
| 4 | KERN_WARNING | 警告 |
| 5 | KERN_NOTICE | 普通但需注意 |
| 6 | KERN_INFO | 提示信息 |
| 7 | KERN_DEBUG | 调试信息 |

> 控制台输出受 `/proc/sys/kernel/printk` 的"控制台日志级别"约束：只有**优先级高于（数字 ≤）该阈值**的 printk 才会在串口/终端打印。修改示例：`echo 8 > /proc/sys/kernel/printk` 让所有等级都打印。

#### 2.2 驱动代码 `week1_demo.c`

```c
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/uaccess.h>
#include <linux/slab.h>
#include <linux/proc_fs.h>
#include <linux/seq_file.h>

#define PROC_NAME "week1_demo"

static char *last_data;          /* 保存用户通过 proc 写入的数据 */
static int data_len;
static int open_count;           /* 统计被打开次数，演示 ko 信息 */

/* 读取 /proc/week1_demo：打印 ko 信息 */
static int week1_proc_show(struct seq_file *m, void *v)
{
    seq_printf(m, "== week1 demo ko info ==\n");
    seq_printf(m, "module name : week1_demo\n");
    seq_printf(m, "author      : tantan\n");
    seq_printf(m, "open_count  : %d\n", open_count);
    seq_printf(m, "last_data   : %s\n", last_data ? last_data : "(none)");
    return 0;
}

static int week1_proc_open(struct inode *inode, struct file *file)
{
    open_count++;
    return single_open(file, week1_proc_show, NULL);
}

/* 写入 /proc/week1_demo：把用户数据拷进内核并打印（各等级都演示一遍） */
static ssize_t week1_proc_write(struct file *file, const char __user *buf,
                                size_t count, loff_t *ppos)
{
    char *tmp;
    tmp = kzalloc(count + 1, GFP_KERNEL);
    if (!tmp)
        return -ENOMEM;

    if (copy_from_user(tmp, buf, count)) {
        kfree(tmp);
        return -EFAULT;
    }

    kfree(last_data);
    last_data = tmp;
    data_len = count;

    /* 演示 8 个等级，受控制台级别过滤 */
    printk(KERN_EMERG   "week1: [EMERG] %s", tmp);
    printk(KERN_ALERT   "week1: [ALERT] %s", tmp);
    printk(KERN_CRIT    "week1: [CRIT] %s",  tmp);
    printk(KERN_ERR     "week1: [ERR] %s",   tmp);
    printk(KERN_WARNING "week1: [WARN] %s",  tmp);
    printk(KERN_NOTICE  "week1: [NOTICE] %s",tmp);
    printk(KERN_INFO    "week1: [INFO] %s",  tmp);
    printk(KERN_DEBUG   "week1: [DEBUG] %s", tmp);

    return count;
}

static struct file_operations week1_proc_fops = {
    .owner   = THIS_MODULE,
    .open    = week1_proc_open,
    .read    = seq_read,
    .write   = week1_proc_write,
    .llseek  = seq_lseek,
    .release = single_release,
};

static int __init week1_demo_init(void)
{
    proc_create(PROC_NAME, 0664, NULL, &week1_proc_fops);
    printk(KERN_INFO "week1_demo: insmod ok, /proc/%s created\n", PROC_NAME);
    return 0;
}

static void __exit week1_demo_exit(void)
{
    remove_proc_entry(PROC_NAME, NULL);
    kfree(last_data);
    printk(KERN_INFO "week1_demo: rmmod ok\n");
}

module_init(week1_demo_init);
module_exit(week1_demo_exit);
MODULE_LICENSE("GPL");
MODULE_AUTHOR("tantan");
```

### test2 —— 用户态交叉编译 socket demo

**需求**
1. 自己写 socket demo；
2. 能编出服务端 + 客户端，同时支持 **x86 虚拟机**和 **iMX6ULL ARM** 平台；
3. 可以 x86↔ARM 通信、x86↔x86 通信（本地走 127.0.0.1）。

#### 2.1 服务端 `server.c`（TCP echo）

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <arpa/inet.h>

#define PORT 8888
#define BUF  1024

int main(void)
{
    int sfd, cfd;
    struct sockaddr_in saddr, caddr;
    socklen_t clen = sizeof(caddr);
    char buf[BUF];

    sfd = socket(AF_INET, SOCK_STREAM, 0);

    saddr.sin_family = AF_INET;
    saddr.sin_port   = htons(PORT);
    saddr.sin_addr.s_addr = INADDR_ANY;     /* 监听所有网卡 */

    bind(sfd, (struct sockaddr *)&saddr, sizeof(saddr));
    listen(sfd, 5);
    printf("server listen on 0.0.0.0:%d\n", PORT);

    cfd = accept(sfd, (struct sockaddr *)&caddr, &clen);
    printf("client connected\n");

    while (1) {
        int n = read(cfd, buf, BUF - 1);
        if (n <= 0) break;
        buf[n] = '\0';
        printf("recv: %s", buf);
        write(cfd, buf, n);                /* 原样回显 */
    }
    close(cfd);
    close(sfd);
    return 0;
}
```

#### 2.2 客户端 `client.c`

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <arpa/inet.h>

#define PORT 8888

int main(int argc, char *argv[])
{
    const char *ip = (argc > 1) ? argv[1] : "127.0.0.1";  /* 默认本机 */
    int fd;
    struct sockaddr_in saddr;
    char buf[1024];

    fd = socket(AF_INET, SOCK_STREAM, 0);

    saddr.sin_family = AF_INET;
    saddr.sin_port   = htons(PORT);
    inet_pton(AF_INET, ip, &saddr.sin_addr);

    connect(fd, (struct sockaddr *)&saddr, sizeof(saddr));
    printf("connected to %s:%d\n", ip, PORT);

    write(fd, "hello socket\n", 14);
    int n = read(fd, buf, sizeof(buf) - 1);
    buf[n] = '\0';
    printf("echo: %s", buf);

    close(fd);
    return 0;
}
```

### test3 —— LED 驱动改用 ioctl（原来是 read+write）

**需求**：把《LED 驱动开发实验》里"用 `write` 控制 LED"的方式改成 **`ioctl`** 实现。下面给出在新字符设备框架（`newchrled`）基础上的改法。

#### 3.1 驱动改动要点

- 用 `_IOW` 定义命令；
- `file_operations` 加 `.unlocked_ioctl`；
- 去掉/保留 `write`（这里用 ioctl 替代写）；
- 应用用 `ioctl(fd, CMD, arg)` 传 0/1。

```c
/* 在 led 驱动里新增（基于《新字符设备驱动实验》newchrled 框架） */
#include <linux/ioctl.h>

#define LED_IOC_MAGIC  'l'
#define LED_ON    _IOW(LED_IOC_MAGIC, 1, int)   /* 开灯 */
#define LED_OFF   _IOW(LED_IOC_MAGIC, 2, int)   /* 关灯 */

static long led_ioctl(struct file *filp, unsigned int cmd, unsigned long arg)
{
    switch (cmd) {
    case LED_ON:
        led_switch(LEDON);     /* 低电平点亮（见原驱动） */
        break;
    case LED_OFF:
        led_switch(LEDOFF);
        break;
    default:
        return -EINVAL;
    }
    return 0;
}

static struct file_operations led_fops = {
    .owner   = THIS_MODULE,
    .open    = led_open,
    .release = led_release,
    // .write = led_write,   /* 旧的 write 方式可删除或保留 */
    .unlocked_ioctl = led_ioctl,   /* 新增：ioctl 控制 */
};
```

> 其它部分（ioremap、时钟/复用/GPIO 方向初始化、`alloc_chrdev_region` + `cdev_add` + `class_create` + `device_create`）**原样保留**，只把"控制通道"从 `write` 换成 `ioctl`。注意 `unlocked_ioctl` 的返回类型是 `long`，函数签名是 `long (*unlocked_ioctl)(struct file *, unsigned int, unsigned long)`。

#### 3.2 测试 APP 改用 ioctl

```c
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>

#define LED_IOC_MAGIC 'l'
#define LED_ON  _IOW(LED_IOC_MAGIC, 1, int)
#define LED_OFF _IOW(LED_IOC_MAGIC, 2, int)

int main(int argc, char *argv[])
{
    int fd;
    if (argc != 3) { printf("Usage: %s /dev/xxx 1|0\n", argv[0]); return -1; }
    fd = open(argv[1], O_RDWR);
    if (fd < 0) { printf("open %s failed\n", argv[1]); return -1; }

    if (atoi(argv[2]) == 1)
        ioctl(fd, LED_ON, 0);    /* 开灯 */
    else
        ioctl(fd, LED_OFF, 0);   /* 关灯 */

    close(fd);
    return 0;
}
```

```bash
# 使用
./ledApp /dev/newchrled 1    # 开灯
./ledApp /dev/newchrled 0    # 关灯
```

> **为什么用 ioctl 更好**：ioctl 是"设备自定义控制"的标准通道，语义比"往文件写 1 个字节"更清晰，可以带多种命令/参数（调亮度、读状态、设模式都行），也避免了 read/write 被用来传递控制字的歧义，是 Linux 驱动里控制类操作的正统做法。

## 三、课后思考：iMX6ULL 启动 vs RV1126 启动

学到的差异点：**RV1126 比 iMX6ULL 在启动前面多了 SPL、TEE OS、ATF，以及加密涉及 eFUSE 硬件**。下面把这几个概念、作用与联系理清楚。

### 1）各概念是什么、干什么

| 概念 | 全称 / 是什么 | 作用 |
|------|--------------|------|
| **SPL** | Secondary Program Loader（二级程序加载器） | 极小的、跑在**芯片内部 SRAM（OCRAM）** 里的第一段软件；负责在 DDR 起来之前初始化**时钟、DDR、电源、引脚**，然后把下一阶段（ATF/TEE/u-boot）从存储设备搬到 DDR 执行 |
| **ATF / TF‑A** | ARM Trusted Firmware（Trusted Firmware‑A） | 运行在 **EL3（安全监视器）**；负责建立安全世界的基础环境、处理 SMC 调用、做"安全启动"签名校验，并**启动 Normal World 的 u-boot/linux**。ARMv8 上它是标准件 |
| **TEE OS** | Trusted Execution Environment OS（如 OP‑TEE） | 运行在 **Secure EL1** 的安全操作系统；向 Normal World（Linux/APP）提供**可信服务**：安全存储、加解密、密钥管理、DRM 等，通过 GP TEE API 调用 |
| **eFUSE** | 芯片内**一次性可编程熔丝** | 硬件级"保险丝"，烧录后不可改；存**安全启动公钥哈希、加密密钥、boot 配置、JTAG 锁定位**等，是信任根（Root of Trust）的硬件锚点 |

### 2）启动链对比

**iMX6ULL（笔记里的流程，无 SPL/ATF/TEE）：**

```text
Boot ROM (BROM)
   └─ 读 IVT+DCD，DCD 初始化 DDR
        └─ u-boot（DDR 中）
             └─ bootz → Linux 内核
                  └─ rootfs
```

**RV1126（多了 SPL / ATF / TEE / eFUSE 加密）：**

```text
Boot ROM (BROM)
   └─ 校验（用 eFUSE 里的公钥哈希验签）后加载 SPL
        └─ SPL（OCRAM 中：初始化 DDR/时钟/电源）
             └─ 加载并跳到 ATF (EL3)
                  ├─ ATF 启动 TEE OS (Secure EL1)   ← 安全世界
                  └─ ATF 启动 u-boot (Normal EL2/EL1) ← 正常世界
                       └─ bootm → Linux 内核
                            └─ rootfs
```

### 3）联系

- **为什么需要 SPL**：BROM 太小太简单，干不了"初始化 DDR + 加载大镜像"的活；SPL 作为"轻量二传手"先在 OCRAM 把 DDR 点亮，再搬后面的重活。iMX6ULL 用 DCD 代替了这一步，所以没有 SPL。
- **为什么需要 ATF**：ARMv8 有了 EL3 安全监视等级，ATF 就是站在 EL3 的"安全总管"，负责验签、切换世界、启动后续；没有它，安全启动和 TEE 都无从谈起。
- **为什么需要 TEE OS**：很多安全业务（指纹、支付、版权保护）不能放在普通 Linux 里，TEE 提供一块"隔离的安全飞地"，由 ATF 托管。
- **eFUSE 串起整条信任链**：它是**硬件信任根**——里面烧着公钥/密钥，BROM/SPL/ATF 逐级用它对下一阶段**验签**，任何一段被篡改都启不来（即"加密/安全启动"）。烧录 eFUSE 一般是出厂或量产前一次性完成，烧完难回头。

> 总结：**iMX6ULL 是"裸奔式"启动（BROM→u-boot→kernel），简单够用；RV1126 是"安全链式"启动（BROM→SPL→ATF→TEE→u-boot→kernel），多出来的 SPL/ATF/TEE/eFUSE 全部围绕一件事：在开机最早阶段建立可信、可验签的安全启动链条。**
